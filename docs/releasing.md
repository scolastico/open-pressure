# GitHub releases

The manual [Release APK workflow](../.github/workflows/release.yml) accepts a SemVer version, commits the app version, pushes the branch, builds a signed APK and publishes it on a GitHub Release. It does not run on ordinary pushes.

## One-time setup

Add these repository Actions secrets under **Settings → Secrets and variables → Actions**:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Base64 encoding of your private Android signing keystore |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | Signing key alias inside that keystore |
| `ANDROID_KEY_PASSWORD` | Password for that key |

Keep the signing keystore backed up privately and reuse it for future releases. Android updates require the same signing identity. The previous locally shared test APKs used a debug key; using a different release key requires exporting local data before uninstalling that test app. No signing key belongs in the repository, and the workflow never falls back to a generated debug key.

The workflow requests `contents: write` through `GITHUB_TOKEN`. Repository/organization settings and branch rules must allow its bot to push the release commit and tag and create releases. It never force-pushes or disables commit signing. Rules requiring signed commits or pull requests need an appropriately configured automation identity/ruleset.

## Run a release

1. Merge the workflow onto the default branch so GitHub offers its manual trigger.
2. Open **Actions → Release APK → Run workflow**, choose the branch and enter a version such as `0.4.0` or `0.4.0-rc.1`. Omit the `v` prefix. Build metadata such as `0.4.0+build.2` is supported.
3. The workflow updates `versionName` and `versionCode` in `app/build.gradle`, creates `chore(release): vVERSION`, and pushes it to the selected branch. All other code remains at that commit.
4. After pushing, it runs protocol, release-unit, storage, locale and release-preparation tests plus Android release lint. It builds, aligns, signs and verifies the APK before tagging that exact commit and uploading `OpenPressure-VERSION.apk`.
5. A draft release is published only after its APK uploads successfully. Versions with a prerelease component are marked as GitHub prereleases; build metadata alone does not make a prerelease. Release notes are generated by GitHub.

## Revision numbers and retries

`versionCode` is the complete number of commits reachable from the release commit: `git rev-list --count HEAD`. Preparation uses the current count plus one, then verifies the count again after committing. Checkout includes full history; shallow history is rejected. This is the revision number, not the workflow run number. Android requires increasing version codes for updates, so preserve repository history and check commit counts when switching release branches. Importing the current source into a new repository can initially produce a count below the manually assigned test-build codes.

If a build or upload fails after its commit was pushed, rerun from that unchanged release commit with the same version. The helper recognizes its version/count/commit message and reuses it. An existing matching tag/draft can also be resumed. Published releases are not overwritten, and an existing tag pointing elsewhere is rejected. If another commit has since reached the branch, use a new version rather than moving an existing release tag.

Test the version helper locally with `python3 tools/test-release.py`. It uses disposable Git repositories and does not commit in your checkout. Workflow syntax can be checked with [actionlint](https://github.com/rhysd/actionlint). Signing follows the Android [apksigner](https://developer.android.com/tools/apksigner) command-line workflow; publishing uses [GitHub CLI releases](https://cli.github.com/manual/gh_release_create).
